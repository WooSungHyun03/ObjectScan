## 1. 강제 제한: 모델 연구 및 외부 권한

### 절대 금지 — 연구·성능 향상

- AI 모델 자체 학습/파인튜닝/교체/성능 비교 실험/PSNR·SSIM·LPIPS 개선/VRAM 효율화 연구/새 렌더러 및 생성 파이프라인 연구/신규 GS 기법/새 논문 구현·실험.
- 현재 OAL/GW/MV 모델이 품질·VRAM 한계로 막혀 있다면 **다른 기술을 개발하거나 학습해 해결하라는 티켓을 만들지 말 것.** 검증된 동작만 지원하고 나머지는 고객에게 정확히 안내할 것.
- 안정적 운영을 위한 기존 추론 실행의 오류 처리·취소·재시도·메모리 초과 안내·파일검증·버전 회귀 테스트는 허용. 이것은 '연구'가 아니라 '제품 안정화'다. GPU 실제 실행 권한/모델 환경을 만져야 하면 Owner-local에 둔다.
- '사용자 기능'처럼 이름을 바꿔 알고리즘 개발 연구를 숨겨 넣지 말 것. 예: 자동 3D 복원 개선, hole filling SOTA, 재질 AI 보정, 자동 리토폴로지 자체 알고리즘 등은 이번 범위 밖.

### 접근 권한 강제 분리

**TEAM (두 팀원 모두):** React/Next.js UI·UX, 기존 API 이용, 클라이언트 편집·뷰어·폼·업로드 경험, 문구, 접근성, 인증/결제 UI의 mock 계약, 기존 라이브러리 활용, 로컬 테스트/fixture, 회귀테스트, 문서, 기존 구현의 안전한 버그 수정. 두 사람은 각각 풀스택 바이브코딩 작업을 맡으며 프론트/백엔드 '역할'을 고정하지 않는다.

**OWNER-LOCAL (사용자의 컴퓨터에서 Codex 실행):** 기존 모델/Worker 설정과 실GPU 진단, 실제 API key/.env/SMTP/Toss client+secret/웹훅, Supabase 스키마·마이그레이션·운영 DB 접근, auth provider 설정, Cloudflare/Vercel/SSL/도메인 배포, 민감한 관리자 설정, DB 백업/복원. 설정 가능한 로컬 작업은 Codex가 실제 수행하며, 로그인/2FA/서비스 대시보드 권한·정책 승인이 필요할 때만 사용자에게 필요한 조치를 구체적으로 요청한다. **키를 채팅·문서·GitHub 이슈에 노출하지 않는다.**

**중요한 경계:** 팀원 작업에 DB 변경이 필요한 신규 기능은 (A) 기존 스키마/API로 해결, (B) 동일 기능 티켓을 '팀원 UI·로컬 계약'과 'OWNER-LOCAL 스키마·서버 실연동'으로 분리. 팀원에게 DB 운영 접근을 요구하지 않는다. 팀원은 mock/local fixture로 완료 증거를 남기며 Owner-local 실연동이 끝나기 전까지 전체 서비스 완료로 표시하지 않는다.

TEST 결제와 실제 현금 거래는 구별하라. UI는 실제 서비스 품질을 지향하되 테스트 카드를 실제 청구로 위장하지 않는다. 실제 마켓 판매액/가짜 후기/가짜 3D 출력물을 만들어 판매 실적처럼 노출하지 않는다. 모델 체크포인트·의존성·출력물 판매권리 검토를 생략하지 않는다.

## 4. 개선 후보 선정과 구현 가능성 심사

각 후보에 대해 반드시 아래를 답하라.

1. **누가 어떤 과업에서 막히는가?** (실제 재현 또는 UX 가설 명시)
2. 경쟁사는 어떻게 해결하는가? (직접 관찰/공식 문서 URL)
3. ObjectScan에서 이미 구현한 것은 무엇이며 왜 부족한가?
4. 신규 AI 연구 없이 어떻게 구현하는가? 우선 `Three.js`, `@react-three/fiber`, `Drei`, `glTF-Transform`, `meshoptimizer`, `three-mesh-bvh`, `sharp`, 기존 Worker/API/Storage/테스트를 활용. 새 라이브러리는 기능·라이선스·의존성·유지보수 비용 평가.
5. 기술적으로 **실제 동작하는 최소 Scope**와 제외 범위는 무엇인가? 얼굴/삼각형 단위 편집이 복잡하면 우선 노드 선택/숨기기/삭제와 crop 한계 안내 등 기존 기능을 고도화. 수작업 알고리즘은 제외.
6. 팀원 티켓에 DB/키/모델/GPU/배포 접근이 있는가? 있으면 분리하고 OWNER-LOCAL 사전 작업으로 옮겨라.
7. 실제 사용 편의가 개선됐는지 무엇으로 테스트하는가? 예: 클릭 수, 잘못된 제출 방지, 파일 roundtrip, 실패 시 재시도, 다계정 격리, Playwright E2E.

후보의 가치를 **사용자 영향(1~5) / 구현 가능성(1~5) / 경쟁 대비 부족(1~5) / 공수(인일) / 의존성 위험(1~5)**으로 평가하고, P0/P1/P2 및 2주 Sprint / 후속 backlog로 정렬하라. 가정과 검증값을 분리하라. 낮은 실현성의 기능을 매력적이라는 이유로 P0에 올리지 않는다.

### 특히 반드시 검토할 '제품 기능' 후보

- 생성 시작 전 실제 가능 모드/사진 장수, 실패 이유, 예상 크레딧/시도 횟수, 작업 상태/재접속/취소/환급 안내

이는 **후보 목록**이다. 기존 구현·현재 문제·공수에 따라 반드시 탈락/병합/후속 처리하라. 불필요한 화면과 기능을 억지로 추가하지 않는다.

## 5. 기존 티켓 강제 재심사 매핑

기존 번호를 유지하되 정확한 조치를 기록하라. **모델 연구·성능 개발 관련 기존 내용은 새 구현 티켓으로 남겨두지 않는다.** GitHub 기록은 가능하면 이슈 본문을 수정하고 변경 이력을 보존하라.

- **OS-01** 지원 범위/오류 계약: 유지·간결화. 고객에게 실제 사용 가능한 작업 범위 노출. Team.
- **OS-02** 가입 확인/비밀번호 복구: 로컬 UI·mock·경로 검증은 Team, 외부 SMTP/키는 Owner-local.
- **OS-03** 중단된 생성 재접속·크레딧 상태: 유지. 기존 Worker/API 계약 재사용. Team.

- **OS-05** GPU 품질·메모리 회귀: 새로운 성능 실험/모델 개선 금지. Owner-local의 기존 추론 '안정성 smoke/오류 복구'로 재정의하거나 품질 연구 부분은 폐기. Team 예산에서 제외.
- **OS-06** 원본/편집 버전 품질 카드: 이미 있는 삼각형/텍스처 정보 재구현 금지. UX 비교·다운로드 가치를 실증할 때만 유지. Team.
- **OS-07** 업로드 선명도/유사 이미지 진단: 기존 sharp 사용, 과도한 AI 없이 구현 가능하면 유지. Team.

- **OS-11** 프로젝트 삭제/자산 정리: 확인 UI·권한/오류 회복은 Team, DB 정합성·storage 정리·migration은 Owner-local.

## 6. 2명 × 2주 — 역할 아닌 '티켓과 실제 공수'로 균형 배분

- 두 사람 모두 바이브코딩. 역할 이름(Frontend/Backend/ML/DB)을 부여하지 마라. `Member A`, `Member B`는 **작업 티켓 묶음**만 다르게 가진다.
- 2주=10근무일/인 기준, 테스트·통합·예상외 오류를 위한 버퍼 최소 20~25%. 따라서 목표 구현 공수는 각 7~8인일, 가능하면 **A와 B 0.5인일 이내** 차이. 일정·공수가 더 정확하게 파악되면 근거와 함께 조정 가능.
- 티켓 크기는 0.5~2인일(테스트/문서/수정 포함). 2인일 넘으면 사용자 관점에서 독립 기능으로 분해하고 AC까지 독립시킨다.
- 두 사람이 동시에 `apps/web/src/lib/server/api.ts`, shared contract, SQL migration 같은 고충돌 파일을 광범위하게 수정하지 않도록 소유 파일과 통합 순서를 설계한다. DB migration은 원칙적으로 Team 대상 아님.
- 각 팀원이 1주차/2주차에 중요한 P0/P1을 적절히 받도록 분배; 다른 사람의 PR에 2일 이상 기다리는 임계경로를 피한다.
- `ticket/OS-xx` feature branch → 리뷰 가능한 PR → 다른 팀원 리뷰 → 공통 dev 통합; API/owner-local 의존성은 mock와 typed contract로 병렬 개발. 통합된 검증되지 않은 코드를 `main`에 직접 push 하지 않는다.
- Owner-local 공수는 두 팀원 합계 15~16인일에 **포함하지 않는다**. 다만 각 Team 티켓의 블로커/인계 계약에는 연결한다.
- P0: 실제 제작·결과 확인·다운로드·구매가 중단/중복/불명 상태가 되는 핵심 장애. P1: 3D 편집 편의/마켓 유용성/생성 가이드/기본 신뢰. P2: 시간이 남으면 후속.
- 일손 부족시 새 멋진 기능보다 **완성된 사용자 경로와 안정성**을 우선하며 P2를 무리하게 끌어올리지 않는다.

## 7. 티켓 작성의 강제 스키마

각 Team 티켓은 아래 모든 항목을 포함한다.

```
ID / 이전 이슈 번호·링크 / 신규 또는 개정 / 이름 / P0-P2 / Member A 또는 B
예상 공수(0.5 단위) / 난이도 / 리스크 / 선행 티켓 / 수정 예정 파일
실제 현재 코드 근거(파일:심볼 / 커밋 SHA / 스크린샷·테스트)
경쟁사 벤치마크(어떤 사용자 기능이 어떤 사이트에 있고 해당 기능 확인 URL)
문제와 사용자 가치 / 재현 경로 / 최소 구현 범위 / 반드시 하지 않을 것
재사용할 현재 컴포넌트·라이브러리·API / 새 의존성 필요 여부
Owner-local 필요 여부: 없음 / 있음(Owner 티켓 ID, mock contract)
Given-When-Then Acceptance Criteria 3개 이상 (정상/실패/재시도 또는 권한)
로컬 실행 및 unit/integration/Playwright E2E / 모바일(360)·태블릿(768)·데스크톱(1440) 증거
완료조건 / 롤백 또는 feature flag / 다른 사용자 데이터·권한 보존
티켓 단독 실행 가능한 Codex 프롬프트 (경로, 파일, 테스트명, 끝낼 조건 포함)
```

Owner-local 티켓에는 `로컬에서 Codex가 자동 처리할 절차`, `사용자만 수행해야 하는 외부 인증·승인 한 단계`, `추가 실계정 접근 없이도 검증할 mock/예제`, `운영 반영 전 안전 확인`, `비밀키 유출 금지`, `사전 백업/rollback`을 명확히 기재한다.

**애매한 티켓 금지:** `UX 개선하기`, `마켓 고도화`, `Mesh 편집 완성`처럼 끝이 불명확한 한 줄 티켓은 허용하지 않는다. 모호한 결과물은 어떤 화면/행동/테스트에서 통과하는지까지 쪼갠다. 모델명과 복잡한 내부 용어는 고객 UI에서 숨기되 개발자 문서에는 정확한 모델 이름을 유지한다.

## 8. 반복 Harness: 분석 품질 게이트

`REPO → CURRENT UX → COMPETITORS → GAPS → FEASIBILITY → PRIORITY → TICKETS → ALLOCATION → REVIEW → REPEAT`

**Gate 1 Evidence:** 최신 로컬 SHA, UI 캡처, 테스트 상태, 실제/모의 데이터 구분. 최소 핵심 사용자 경로 8개 재현. 미접근 이유 문서화.

**Gate 2 Benchmark:** 경쟁 서비스 4개 이상의 공식 근거 URL과 주요 과업별 기능 확인/미확인. 날짜 기재. 광고성 기능명과 실제 체험 가능 기능을 구분.

**Gate 3 Implementability:** 팀원 티켓 100%에 재사용 코드 경로·권한 검토·공수·테스트 있음. 모델 연구와 실서비스 비밀/운영 DB/배포 접근을 요구하는 티켓 0개.

**Gate 4 Coverage:** 기존 OS-01~18, OWN-01~05 모두 `keep/update/split/defer/obsolete/owner-local` 중 하나로 매핑. 중복 이슈 없고 선행 그래프에 순환 없음.

**Gate 5 Balance:** A/B 각각 7~8일 내외, 공수 차이 0.5인일 이하, 통합 버퍼 20~25%, 첫 작업 착수 가능한 Ready 티켓 1개 이상씩.

**Gate 6 Quality:** 티켓의 정상/오류/권한/모바일 검증 및 Codex 단독 실행용 프롬프트 존재. 티켓 재설계만으로 기능 완료 표시 금지.

하나라도 만족하지 못하면 변경 근거를 남기고 티켓·배분·범위를 다시 수정하라.

- 검사한 저장소/커밋, 실제 이슈 수정/생성 여부, 테스트 증거와 미확인 사항.

## 10. 시작 지시

이제 추측하지 말고 **로컬 실제 코드 및 업로드된 기존 티켓 인덱스부터** 읽어라. Meshy와 유사 사이트를 확인하고, 모델 성능 연구 없는 제품 기능을 골라 티켓을 재작성해라. A/B 균형·Owner-local 분리를 엄격히 지키고 결과를 `docs/product-audit-v2/` 및 GitHub 이슈에 반영하라. 개인 키·운영 DB·DNS·PG 대시보드 접근은 팀원에게 절대 요청하지 않는다. **도메인 교체 결정은 이미 내려졌다**. 허용된 범위에서 문서와 티켓 생성·수정은 실제로 실행하되, 구현과 운영 배포를 완료했다고 거짓 보고하지 마라.
