## 2. 경쟁 서비스 정밀 리서치
공식 서비스 화면, 최신 공식 문서/가격표, 도움말, 릴리스 노트, 공개 사용 후기(가능하다면)를 **최신 날짜 기준으로** 조사하라. 최소 Meshy·Tripo·Polycam·KIRI Engine을 깊이 분석하고, 고객군이 유사한 다른 2~3개만 추가하라. 사이트를 볼 수 없거나 인증/유료 플랜 때문에 확인 불가능하면 그 한계를 표기.

평가축:
- 랜딩/가입/첫 생성까지 단계 수, 한국어 품질, 모바일, 탐색·상태 안내·에러 복구
- 사진 1장 / 2~20장 / 21~100장 이상 / 장면 전체 복원과 입력 촬영 안내
- 복잡한 배경에서 객체 선택·마스크 수정·이미지 제외·카메라 정합 품질 안내
- 형상 품질, UV 및 PBR 텍스처, 실제 입력 반영, 재시도, 결과 비교(가능한 범위만)
- 3D 뷰어, Mesh 크롭·삭제, 위치·회전·크기, decimation/remesh, export, 모델 버전 관리
- 마켓플레이스 탐색·게시·미리보기·구매·소유/다운로드 권한·평점/신고
- 요금/크레딧/결제의 투명성, 실패 처리, 저장 용량/보관 기간
- 성능·모바일·웹 접근성·온보딩·도움말·상담·신뢰 형성

**모든 주요 비교 결과는 근거 URL + 확인일 + 검증 유형(직접 사용/공식 문서/외부 후기/추정)을 함께 기록**. 정량값·가격·성공률을 만들어내지 말 것. 별도 플랜에서만 가능한 기능은 명확히 구분.

출력할 비교표 필수 컬럼: `영역 | 경쟁사/기능 | 경쟁사 근거 | ObjectScan 현재 상태·증거 | 사용자에게 미치는 영향 | 격차 심각도(1~5) | 개선 제안 | 구현 비용·GPU/서버 영향 | 우선순위`.

## 3. 차별화는 모방이 아닌 '이기는 포인트'로 정의
Meshy의 모듈/에셋 제작 흐름을 무작정 복제하지 말 것. ObjectScan 고유 강점 후보를 아래처럼 검증하되, 채택을 미리 확정하지 마라.
- **복잡한 배경에서 원하는 객체만 선택**해 Mesh 생성하고, 여러 장에 걸쳐 동일 대상 마스크를 검토/수정하는 워크플로
- **이미지 수·촬영 조건 자동 진단**: 선명도·중복/유사 뷰·시점 커버리지·정합 실패 사유·추가 촬영 가이드
- **객체와 장면의 2가지 제작 모드**, 입력 장수에 따라 내부 처리 자동 라우팅(외부 모델명 비노출)
- **촬영부터 편집·거래까지 하나의 한국어 워크플로**: 생성→고장난 표면 정리→텍스처 보존→다양한 파일 형식→마켓 게시
- 실패/저품질 결과에 대한 투명한 사유·재업로드 가이드·안전한 재시도 UX
- **마스코트 기반 일관된 온보딩**과 간결한 Meshy 수준의 제품 UX

각 아이디어는 `타깃 사용자·문제·경쟁사 대비 차이·예상 가치·대체 오픈소스·구현 범위·리스크·품질 측정법·추정 공수`로 점수화. 최소 8개 후보를 제시하되 **최종 추천은 2주 내 효과가 큰 2~3개로 압축**. 멋있어 보여도 RTX 4080 16GB에서 실험 불가능하거나 2주 내 만들 수 없는 기능은 후순위/연구 백로그로 보낸다. 3D 자동 리깅/고품질 생성형 텍스처 페인팅처럼 무거운 영역은 근거 없는 약속을 하지 마라.

## 4. 구현 가능성 검사 및 선행 조건
- 각 개선안에 사용 가능한 **실제** 오픈소스/라이브러리를 조사하라: 예: Three.js / React Three Fiber + TransformControls, three-mesh-bvh, glTF-Transform, Blender headless, xatlas, Trimesh, Open3D, SAM2, COLMAP. 기능 지원 여부·입출력·버전·유지보수 상태를 확인하라.
- GPU 16GB, 1개 Worker, 파일 크기, 저장소, 메모리, 모델 환경 충돌, Pose, UV Texture, 사용자 간 권한 문제를 검토. 프런트/백/API/DB/Worker 간 변경 범위를 파일 단위로 파악.
- 마스크 오류, 카메라 정합 실패, OOM, 작업 취소/재시도, 작업 중 브라우저 종료, GLB 유효성/UV 누락, 결제 중복 승인, 비공개 파일 유출 등의 실패 경로를 포함.
- 신규 서비스나 외부 API가 필요하면 **팀원은 키 없이 로컬 mock/테스트 계약까지 구현**하고, 본인이 나중에 연결할 수 있게 `.env.example`·설정 가이드·검증 체크리스트 제공. 실 API 키를 이슈나 Git에 기록하지 마라.
- 카드 결제는 Toss TEST 환경, 판매자 정산은 테스트 원장/수동 요청까지만; 실제 금전 이전이나 실계정 정산을 작동시킨 것처럼 표시 금지.
- 모델/에셋 라이선스와 외부 이용 조건은 확인해 위험으로 기록하되, 연구용 시연과 실제 결제 운영을 구분하라.

## 5. 티켓 우선순위, 범위 및 품질
제일 먼저 사용자에게 실제 가치가 전달되는 End-to-End 경로의 누락부터 해결하라.
- P0: 가입→업로드→대상 선택/장면 선택→작업 생성/상태→진짜 Textured Mesh 미리보기·다운로드가 끊기지 않음, 보안·데이터 정확성.
- P1: 업로드/마스크/촬영 품질 UX, 기본 Mesh 편집·저장, 프로젝트 관리, 한국어 다크 브랜드, 합리적인 요금/테스트 결제/마켓 기본 거래.
- P2: 차별화 확장, 품질 비교/가이드 고도화, 고급 모델 편집·마켓 고급 기능.

진짜 사용 가능한 MVP를 2주 안에 완성할 수 있는지 판단하고, **P0 기능 미완이면 P2 확장 티켓을 2주 Sprint에 넣지 마라**. 팀원 총 가용 작업일은 기본 `2명 × 10근무일 = 20인일`이며, 장애·통합·리뷰 버퍼 **20~25%**를 확보해 순수 계획 개발량은 **15~16인일 이하**로 제한. 로컬 환경·실무 가능 시간이 다르다면 가정을 명시하고 재계산. AI가 코딩해도 설계/오류 수정/통합 시간은 0이 아니다.

티켓은 대체로 0.5~2인일의 검증 가능한 **작은 vertical slice**로 나누라. 2일을 초과하면 분해. 각 티켓이 '하나의 사용자/운영자 문제를 처음부터 끝까지 해결'하도록 정의. 같은 파일을 동시에 크게 바꾸는 충돌을 피하고 공유 계약 티켓을 먼저 배치.

## 6. 팀원 두 명에게 역할이 아니라 티켓의 일감으로 균등 배분
- 이름은 `팀원 A`와 `팀원 B`로 임시 표기. **둘 다 프런트·백엔드·DB·UX·3D 기능 관련 티켓을 섞어서** 배분해 특정 직무를 담당하도록 만들지 마라.
- 각 티켓을 `난이도(S/M/L)`, `예상 인일`, `불확실성`, `의존성`, `동일 파일 충돌 위험`, `인수 기준`으로 측정하고 Critical Path와 병렬 처리 가능성을 따져 배분.
- **두 사람의 총 추정 공수 차이를 10~15% 이내**로 목표. 단, 지나치게 공수를 맞추려고 의존성이 꼬이거나 병렬 작업이 불가능해지지 않게 한다.
- D1~D10 기준 2주 스프린트 보드(순서, 담당, 의존, 시작 조건, 완료 조건)를 작성. WIP limit=각 팀원 1~2, PR 단위 통합, 최소 하루 한 번 smoke 및 lint/test/build, UI 변경은 Playwright 스크린샷 비교.
- **사용자(본인) 전용 Owner 티켓은 별도 표**로만 작성: API 키 발급/입력, Supabase/Vercel/Cloudflare/Toss 계정 연결, 실제 인증, DNS·도메인, 프로덕션 배포·승인, 외부 서비스의 운영 정책 결정. 팀원에게는 이 중 어느 것도 할당하지 말 것. 단, 연결을 위한 코드·설정 예제·가이드 작성은 팀원 티켓.
- Owner 대기로 막히지 않게 stub/mock/preview 환경과 인터페이스를 먼저 작성하도록 의존성 관리. Owner 티켓은 개발 공수 배분에 산입하지 마라.
- 두 사람이 모두 바이브코딩이므로 **티켓 본문에 Codex가 바로 실행할 수 있는 작업 지시(범위·파일 탐색 경로·반드시 확인할 상태·테스트 명령·검증 증거)**를 포함하고, 1개의 티켓은 AI 에이전트가 독립 브랜치에서 완결할 수 있도록 한다.

각 구현 티켓의 필수 템플릿:
```text
ID / 제목 / P0~P2 / 담당(팀원 A 또는 B) / 예상 공수(인일)
문제와 사용자 가치
현재 상태와 근거(파일 경로, 화면, 실패 재현 절차)
구현 범위(In Scope) / 제외 범위(Out of Scope)
권장 접근 및 재사용할 라이브러리
관련 파일·컴포넌트 및 선행 티켓
API/DB/모델 계약 및 오류·취소 상태
Acceptance Criteria (Given/When/Then, 최소 3개)

Definition of Done / 위험·Rollback / 외부 Owner 의존성

```

## 7. 반드시 작성할 산출물
프로젝트의 `docs/product-audit/` 아래 다음 파일을 만들라 (기존 문서와 충돌하면 정리하고 링크):
1. `01_CURRENT_STATE_AUDIT.md` — 로컬/원격/배포의 차이, 화면별 기능 인벤토리, 증거와 미확인 항목.
2. `02_COMPETITOR_MATRIX.md` — 최소 4개 서비스, 기능별 근거 URL·확인일·플랜/검증 구분.
3. `03_GAP_AND_UX_AUDIT.md` — 현재 문제, 심각도, 재현 가능성, 사용자 영향, 스크린샷 인덱스.
4. `04_DIFFERENTIATION_AND_FEASIBILITY.md` — 차별화 아이디어 8개 이상, 후보 평가/추천 2~3개, 오픈소스와 기술 위험, 하지 않을 기능.
5. `05_PRIORITIZED_BACKLOG.md` — P0/P1/P2, 모든 추가·미완성 기능을 구현 범위와 예상 비용으로 정리.
6. `06_TWO_PERSON_SPRINT.md` — 팀원 A/B 역할 분담 금지, 일감 기준 공수 균형·병렬화·D1~D10 계획, 20~25% 버퍼.
7. `07_OWNER_ONLY_ACTIONS.md` — 본인만 할 수 있는 키/계정/DNS/배포 승인 티켓 및 팀원 선행 준비.
8. `08_TICKET_INDEX.md` — 실제 GitHub Issues URL 또는 준비된 티켓 링크·상태·담당·완료 조건.
9. `tickets/*.md` — 각 티켓별 실행 가능한 완성된 이슈 본문.
10. `EVIDENCE_INDEX.md` — 조사 출처·화면·명령·테스트 결과·분석 시각.

GitHub Issue 생성 권한이 있다면 `P0`, `P1`, `P2`, `dev-A`, `dev-B`, `owner-only`, `blocked`, `research`, `security`, `ux` 등 명확한 라벨과 2-week milestone을 사용해 일괄 생성. **중복 Issue가 이미 있으면 새로 만들지 말고 연결/갱신**. 권한이 없으면 모든 이슈를 Markdown으로 작성하고 `gh issue create` 예시를 제공. 다른 사람의 브랜치나 운영 설정을 변경하지 말 것.

## 8. 실행 Loop와 종료 기준
매 단계에서 `Research → Evidence → Gap → Feasibility → Cost → Priority → Ticket → Dependency Review → Load Balance → Quality Review`를 반복하라.

품질 게이트:
- 근거 없는 경쟁사 기능/가격/성능 주장 0건; 확인 불가는 명확히 `미확인`.
- ObjectScan 실제 구현 vs 문서상 설계 혼동 0건.
- P0 누락과 미구현을 숨기지 않고 2주 범위를 현실적으로 축소.
- 모든 티켓에 담당자/공수/인수 조건/검증법/선행 의존/AI 코딩 실행 지시 존재.
- 2명 총 예상 개발량 균형을 수치로 설명하고 Owner 전용 작업이 팀원에게 잘못 배정되지 않음.
- 위험한 실사용 결제·민감 키·배포·DNS를 건드리지 않음.

**최종 보고서를 한국어로 작성하고 아래 순서로 요약**하라:
1. ObjectScan 현 상태에 대한 검증된 핵심 사실 5개
2. 경쟁 서비스 대비 가장 심각한 결함 TOP 10
3. 가장 가치 있는 차별화 기능 TOP 5와 선택 이유
4. 2주에 반드시 완료할 P0/P1 티켓 (전체 수/총 인일)
5. 팀원 A 티켓 ID 목록·공수 합계, 팀원 B 목록·공수 합계 (직무 분할 절대 금지)
6. 본인만 가능한 Owner 티켓 목록
7. 2주 이후 백로그와 의도적으로 제외한 기능
8. GitHub Issue/문서 링크, 조사·검증의 한계

이제 로컬 저장소와 실제 서비스부터 철저히 조사하라. **현재 코드 상태를 모르는 상황에서 티켓을 가정으로 만드는 것부터 시작하지 마라.** 계획서만 잘 쓰는 것이 아니라, 팀원 2명이 즉시 Codex에 복사해 실행 가능한 티켓을 만드는 것이 목표다.
